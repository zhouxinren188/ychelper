# 快速打标查询功能维护说明

> 适用基线：从 `v1.0.78` 主线创建的 `feature/quick-labeling` 分支
> 最后复查：2026-08-18
> 范围：快速打标中的店铺会话、商品查询、SKU 展开、价格/数量筛选、进度、表格选择、TXT 导出及发送到打标/下标

## 1. 阅读顺序

重新接手时建议依次阅读：

1. `src/index.html` 中 `page-shopManage`：界面字段和操作入口。
2. `src/js/renderer.js` 中“店铺管理模块”：配置恢复、店铺切换、查询状态、结果表格和后续操作。
3. `preload.js` 中店铺管理 IPC：渲染层与主进程的边界。
4. `main.js` 中“店铺管理”和“店铺商品查询”：账号分区、Cookie 恢复、页面签名环境、HTTPS 请求与结果转换。
5. `src/js/shopGoodsQuery.js`：可单测的请求参数、响应解析、价格筛选和分页/SKU 串行流程。
6. `src/js/shopGoodsSelection.js`：每个 SPU 的 SKU 选择及最终 SKU 去重。
7. `tests/shop-goods-query.test.js`、`tests/shop-goods-selection.test.js`：当前行为契约。

## 2. 问题与需求背景

原快速打标查询曾有以下问题或需求：

- 直接从普通自动化环境请求京东接口容易触发 `code:601` 风控或 `code:312` 签名校验失败。
- 需要参考老款工具的稳定顺序：每取一页 SPU，立即串行查完本页所有 SKU，再查询下一页 SPU；每个业务响应结束后约等待 300ms。
- 查询条件需要支持精确到分钟的时间范围、全部商品/售卖中/已下架、售价范围。
- “单品 SKU”必须按每个 SPU 单独执行全部、首个、末个、最低价、最高价、前 N 个、随机 N 个；价格筛选必须先执行。某 SPU 价格筛选后不足 N 个时保留全部剩余项，不重复补足。
- 查询过程需要页数、SPU/SKU 进度和预计剩余时间。
- 查询结果要能按 SPU 展开、全选或整组勾选，并导出 TXT、发送到打标或下标。
- 商品列表需要在不重复占用“商品编码”“SKU 编号”列的前提下，提高信息层级和可读性；查询操作按钮需要居中呈现。
- 查询结果需要支持本地右键管理：按 SPU/SKU 动态勾选或取消勾选，并能从当前结果删除整组 SPU 或单个 SKU。
- 店铺账号需要独立 Cookie 分区、重启恢复、在线状态检测和账号切换保护。

## 3. 原因分析

### 3.1 风控与签名失败

当前有效方案不伪造整套页面请求，也不篡改 `XMLHttpRequest`/`fetch`。软件保留已登录的正常店铺后台页面，只做两件必要的事：

1. 从商品页自己的官方请求捕获当前页面的 `dsm-eid`/`dsm-platform` 环境信息，值不写日志。
2. 调用该页面已经加载的官方 `ParamsSign` 生成本次请求的 `h5st`，主进程再通过单连接 Keep-Alive HTTPS 串行请求 SFF API。

请求 Cookie 只带老款实测需要的 `thor` 和 `flash`。随意增加 Cookie、请求头、页面注入或并发量都可能改变风控结果。

### 3.2 SKU 卡住或请求过密

旧实现存在过多页面点击、XHR 拦截和环境伪装尝试。当前活跃链路固定为：

```text
第1页 SPU
  → SKU 1 → 等待300ms
  → SKU 2 → 等待300ms
  → ...
第2页 SPU
  → 本页 SKU...
```

SKU 请求超时为 30 秒，HTTPS Agent 固定 `maxSockets: 1`，不允许同一查询并发请求。

### 3.3 筛选语义混淆

售价是 SKU 级条件；“单品 SKU”是对价格筛选后的每个 SPU 分组取值。因此正确顺序是：

```text
京东商品状态/时间筛选
  → 完整展开 SKU
  → SKU 售价筛选
  → 每个 SPU 分别取 SKU
  → 用户勾选
  → 导出或发送
```

不能先随机 N 个再筛价格，否则某些符合价格的 SKU 会无故丢失。

### 3.4 本轮全面检查发现的问题

本轮在现有功能上又发现并修复了以下确定问题：

1. **每个 SPU 第一条 SKU 会重复提交**：SPU 主行复用了第一条 SKU 的 `data-idx`，同时第一条 SKU 子行又有同一索引，默认全选导出/发送时会重复一次。
2. **无价格 SKU 绕过售价范围**：旧过滤条件允许 `price == null` 直接通过，与“先按价格筛选”的语义不符。
3. **最低价高于最高价未拦截**：会静默得到空结果，用户难以判断是无数据还是配置错误。
4. **服务端下调分页大小时可能漏页**：请求 100 条但响应实际 `pageSize=50` 时，旧代码仍按 100 计算总页数。
5. **查询期间可切换/删除/重登当前店铺**：可能销毁正在签名的页面，甚至混用不同账号的页面环境和 Cookie。
6. **查询异常后旧结果操作按钮可能仍可用**：IPC 抛错、空结果或失败时存在继续导出旧数据的可能。
7. **空 SKU 或重复 SKU 可进入后续操作**：异常响应可能产生空编号；表格索引重复也缺少最终去重防线。
8. **SFF 业务体明确表示登录失效时未统一下线**：HTTP 仍为 200 时，旧代码可能只显示普通接口错误。
9. **商品编码缺失时表格错误合组**：多个缺少 `productCode` 的异常记录会被合并成一个 SPU。
10. **原始价格异常可能显示 `¥NaN`**：价格转换失败未统一归一化为空。

## 4. 当前修改方案

### 4.1 店铺与查询绑定

- 渲染层发起查询时必须带当前 `accountId`。
- 主进程校验请求账号必须等于 `activeShopAccountId`。
- 查询期间禁用店铺下拉、管理、登录/重登和结果操作按钮。
- 主进程同时拒绝查询期间切换账号、重新登录或删除当前账号。
- 查询过程每次请求前再次确认活跃账号没有变化；渲染结果返回时也校验店铺没有变化。

### 4.2 请求与分页

- 商品页固定使用官方 `ParamsSign` 生成签名。
- SPU 与 SKU 全程串行，请求响应完成后至少间隔 300ms。
- 首屏以响应中的真实 `pageSize` 计算总页数，防止服务端限流或下调页大小造成漏查。
- HTTP 401/403、登录跳转、业务码/消息明确表示未登录或会话失效时，标记店铺离线并提示重新登录。
- `code:312` 仍归为签名错误，`code:601` 仍归为风控错误，不误判为 Cookie 失效。

### 4.3 数据映射与筛选

- SKU 接口有有效数据时使用完整 SKU；返回 0 条时使用 SPU 列表附带的单 SKU 作为兜底。
- SKU 项缺少 `skuId` 时跳过；兜底也没有 SKU 编号时跳过该商品并记录警告。
- 无法解析的价格统一为 `null`，不显示 `NaN`。
- SPU 主标题统一使用商品列表返回的 `productName`，不拼接 SKU 规格；展开后的 SKU 子行单独使用 `skuName`，若 SKU 名称仅等于 SPU 标题，则从 `saleAttrs` 补回规格选项。SPU 标题缺失时才回退到 SKU 名称。
- 商品状态优先读取每个 SPU 响应中的状态名称或 `productState` 等状态码（`4` 为售卖中、`5` 为已下架）；响应缺失状态时，仅在查询明确限定售卖中/已下架时使用筛选值回退。“全部商品”缺失实际状态时显示“未知”，不得猜测。
- 未设置价格范围时保留全部 SKU；设置任一价格边界后，只保留具有有效数字价格且满足边界的 SKU。
- 价格筛选后，再调用 `selectGoodsPerProduct` 按每个 SPU 独立取值。
- “前 N 个”和“随机 N 个”都使用 `min(N, 当前 SPU 剩余 SKU 数)`。

### 4.4 表格选择与后续操作

- SPU 主行使用独立的 `.sm-spu-check`，只控制该组 SKU，不再代表第一条 SKU。
- 商品列表使用独立的现代分组表格：不单独占列重复显示商品编码和 SKU 编号；SPU 主行在标题下显示 `SPU：编码 · 共 N 个 SKU`，SKU 子行显示包含规格选项的 SKU 标题，并在副标题中显示 `SKU：编号`；“状态”列位于“操作日期”前，并在主行和子行显示售卖中/已下架徽标；样式调整不得改变主行/子行勾选语义。
- 实际导出/发送只读取 `.sm-sku-row .sm-goods-check`。
- SPU 组勾选和全选支持 `indeterminate` 半选状态。
- 商品行右键菜单会根据当前行状态显示“勾选”或“取消勾选”：SPU 行控制整组 SKU，半选按未全选处理并显示“勾选”，SKU 行只控制当前 SKU；菜单也支持从当前结果中删除，右键 SPU 删除该商品的全部 SKU，右键 SKU 只删除当前 SKU。删除只更新本地查询结果，不调用京东接口，并保留其他行的勾选与展开状态。
- 最终 SKU 列表按原顺序去空、去重，作为最后一道防线。
- 失败、异常和空结果都会清空结果并禁用导出/发送按钮。

## 6. 当前数据流

```text
用户选择店铺
  → switch-shop-account
  → 按账号 UUID 使用独立 persist 分区
  → 从 Cookie 文件恢复并通过身份接口验证
  → 查询按钮可用

用户点击“查询商品”
  → 校验权限、店铺、时间、价格
  → shop-query-goods(accountId, filters)
  → 打开/复用隐藏的正常店铺页面
  → 导航到商品列表页
  → 捕获官方 dsm-eid
  → 页面 ParamsSign 生成 h5st
  → 第1页 SPU
  → 本页逐个 SKU（响应后间隔300ms）
  → 后续 SPU 页及各页 SKU
  → 数据映射
  → SKU 价格过滤
  → 返回渲染层
  → 每个 SPU 数量过滤
  → 表格显示与勾选
  → TXT / 打标 / 下标
```

## 8. 风险点与已知限制

1. **第三方接口变化**：SFF API、`ParamsSign`、字段名、`dsm-eid` 或 Cookie 要求由京东控制，随时可能变化。先采集脱敏日志和真实官方请求结构，再修改；不要猜测补头。
2. **风控风险**：`312` 与 `601` 不是普通网络重试错误。短时间自动重试可能加剧风险，当前设计直接停止并提示处理。
3. **查询耗时**：流程为稳定性刻意串行，无取消接口；大店铺可能运行数分钟。不要为了提速直接并发 SKU。
4. **SKU 0 条兜底**：接口返回 0 条时只使用商品列表附带 SKU；如果连兜底编号也没有，该商品会被跳过并写警告。
5. **内存占用**：全部 SPU 与 SKU 在内存中组合后再返回渲染层，极大店铺仍需关注内存和 IPC 负载。
6. **账号存储**：店铺 Cookie 按账号记录 UUID 隔离，而不是按商家 ID 命名。账号密码仍属于店铺账号模块的敏感数据，日志中禁止输出。
7. **无请求取消**：当前关闭页面或退出应用只能终止任务，没有面向用户的“取消查询”按钮。
8. **历史代码干扰**：`src/js/shop-preload.js`、`src/js/chrome-shop-query.js` 以及 `main.js` 中页面点击/XHR 拦截相关函数是旧方案，目前没有被活跃链路加载。不得因为它们存在就误以为当前查询依赖反指纹、弹窗隐藏或 XHR 篡改，也不得未经重新评估直接启用。
9. **权限**：界面允许所有用户进入，但实际查询、管理、导出和发送只允许有效试用用户或有效高级版用户；渲染层和主进程都有校验。
10. **本地删除无撤销栈**：右键删除只修改当前内存结果，不会调用京东接口；误删后需要重新查询恢复。SPU 删除按原始查询结果移除该商品的全部 SKU，即使当前“单品 SKU”筛选只显示其中一部分。

## 9. 维护规则

1. 保持请求顺序为页优先串行，保留 300ms 响应后间隔和单连接 Agent；调整频率必须有新的真实抓包证据。
2. 时间/状态尽量由商品列表 API 过滤；价格必须作用于完整 SKU；每 SPU 取值必须最后执行。
3. 新增筛选条件时明确它属于 SPU 级还是 SKU 级，并把顺序写进测试。
4. 任何账号切换都必须同时切换 Cookie 分区、页面窗口、内存状态和 `activeShopAccountId`，不能只改下拉框。
5. 进度事件应保持单个查询单飞；若以后增加取消/重试，必须加入查询 ID，防止旧事件污染新任务。
6. 表格主行只负责分组展示和整组选择，不能对应真实 SKU 索引；后续操作只读取 SKU 子行并最终去重。
7. 不把 Cookie、`thor`、`flash`、`h5st`、`dsm-eid` 值、账号或密码写入日志。当前日志只记录头名称和业务计数。
8. 京东响应字段变化时先把数据转换抽成可单测纯函数，再改 UI；不要继续在 `main.js` 堆叠不可测试分支。
9. 修改 `main.js`、`preload.js` 或 `src/js/shopGoodsQuery.js` 后，如以后获得发布授权，按 `AGENTS.md` 必须发布新的三段完整安装包，不得只做热更新。`shopGoodsQuery.js` 虽位于 `src/`，但由主进程直接 `require`。
10. 开发分支不等于发布授权；未明确要求发布时不得改版本号、构建或上传更新。
11. 右键删除必须继续同时更新 `smGoods` 与 `smFilteredGoods`，并保留剩余 SKU 的勾选状态和 SPU 展开状态；右键勾选只能作用于当前表格结果，不能触发查询或改变价格/单 SPU 筛选顺序。
